GUIA DE COMPONENTES E ESTRUTURA DO FRONTEND
==========================================

Este guia apresenta a organização atual do frontend, os componentes que podem
ser reutilizados e as convenções para implementar novas telas.


1. MAPA DAS PASTAS
------------------

frontend/src/
  App.jsx                 Rotas da aplicação.
  main.jsx                Inicialização do React, do roteador e dos estilos.
  api/                    Integração com endpoints da API.
  assets/                 Imagens, ícones e outros arquivos estáticos.
  components/             Componentes reutilizáveis da interface.
    common/               Componentes compartilhados entre áreas/telas.
    post/                 Componentes de publicações.
    comment/              Componentes de comentários.
    user/                 Componentes relacionados ao usuário.
  contexts/               Contextos React compartilhados.
  data/                   Dados mockados ou fixtures para desenvolvimento.
  features/               Componentes e estilos agrupados por funcionalidade.
    auth/                 Elementos específicos da autenticação.
  hooks/                  Hooks React reutilizáveis.
  layouts/                Estruturas que envolvem páginas e rotas.
    auth/                 Layouts de autenticação.
    user/                 Layouts da área do usuário.
  pages/                  Telas associadas às rotas.
    auth/
    feed/
    posts/
    profile/
    search/
    settings/
    about/
    support/
    terms/
    admin/
    faq/
  routes/                 Configurações auxiliares de rotas, se necessárias.
  services/               Lógica de serviços e acesso a dados.
  styles/                 Estilos globais e estilos base.

Use os nomes de diretório existentes em inglês e mantenha cada arquivo na pasta
que representa melhor sua responsabilidade.


2. COMPONENTES REUTILIZÁVEIS JÁ IMPLEMENTADOS
---------------------------------------------

COMPONENTES COMUNS — src/components/common/

  Header.jsx
    Cabeçalho da área do feed, com marca, busca, botão para postar dúvida e
    avatar.
    Props atuais:
      onPostQuestion: função chamada ao clicar em "Postar dúvida".
      userName: texto acessível do botão de perfil.
      userAvatarUrl: endereço opcional da imagem do usuário.

  Background.jsx
    Fundo visual da área principal. Recebe children e envolve o conteúdo que
    deve aparecer acima das decorações.

  MainNavigation.jsx
    Navegação lateral. Recebe items, um array com objetos no formato:
      { to, label, icon, end }
    Itens sem "to" são apresentados como indisponíveis.

  ProfileSummary.jsx
    Resumo do perfil. Recebe name, followingCount, followersCount e avatarUrl.
    Os dados possuem valores padrão para que o componente também possa ser
    usado sem todas as props.

  OptionList.jsx
    Lista de opções agrupada sob um título, usada na tela de configurações.
    Recebe id (usado no id acessível do título), title, items e onSelect.
    Cada item tem o formato:
      { id, label, description, icon, to, action, tone }
    Itens com "to" navegam; itens com "action" chamam onSelect(action);
    itens sem nenhum dos dois aparecem como "Em breve". tone "danger" destaca
    ações como sair da conta.

  SubjectTag.jsx
    Etiqueta de conteúdo/matéria, usada nos posts e na busca. Recebe name e,
    opcionalmente, onRemove para exibir o botão de remover.

  TagSearchInput.jsx
    Campo de busca com etiquetas. Ao digitar "#texto" seguido de dois espaços,
    chama onAddTag(texto) e mantém o restante em query. Backspace com o campo
    vazio remove a última etiqueta. Recebe id, label, placeholder, query, tags,
    onQueryChange, onAddTag e onRemoveTag(index).
    Opcionalmente recebe suggestions (lista de nomes): elas aparecem abaixo do
    campo e podem ser escolhidas com clique, setas, Enter ou Tab. A página
    decide quais sugestões mostrar (na Explorar, matérias que combinam com o
    texto digitado depois do "#").

  FormField.jsx
    Campo de formulário com rótulo, dica, contador de caracteres e erro.
    Recebe id, label, hint, error, multiline (usa <textarea>), value,
    maxLength e prefix (ex.: "@"); as demais props vão para o campo.

  ToastProvider.jsx
    Exibe avisos temporários (toasts) no rodapé da tela por 4 segundos. Fica
    em main.jsx, envolvendo toda a aplicação. Para disparar um aviso, use o
    hook src/hooks/useToast.js:
      const showToast = useToast()
      showToast('E-mail enviado com sucesso.')
      showToast('Algo deu errado.', { type: 'error' })

  ConfirmDialog.jsx
    Janela de confirmação para ações importantes. Recebe title, description,
    confirmLabel, cancelLabel, tone ("danger" deixa o botão vermelho),
    isConfirming, canConfirm, onConfirm e onCancel (use useCallback, pois é
    dependência do efeito que trata o Esc). children aparece antes dos botões.

  InfoList.jsx
    Lista somente leitura de informações, agrupada sob um título (usada em
    Informações da conta). Recebe id, title e items no formato
    { id, label, value, icon, hint }; value vazio aparece como
    "Não informado".

  BackLink.jsx
    Link "Voltar" com seta, usado no topo das telas internas. Leva sempre à
    tela aberta antes desta e mostra o nome dela (ex.: abrir o perfil pelas
    Configurações mostra "← Configurações"). Recebe to e label como destino
    padrão, usado só quando não há tela anterior (endereço aberto direto).
    A ordem das telas é guardada por NavigationHistoryProvider (em main.jsx)
    e lida pelo hook src/hooks/useBackTarget.js. Os nomes das telas ficam em
    src/routes/routeLabels.js: ao criar uma rota nova, adicione o nome lá.

  FaqItem.jsx
    Pergunta expansível do FAQ, baseada em <details>. Recebe question e
    answer. A lista de perguntas fica em src/data/mockFaqs.js.

COMPONENTES DE USUÁRIO — src/components/user/

  AccountSummaryCard.jsx
    Cartão com avatar, nome, username, curso e semestre da conta autenticada.
    Recebe user com name, username, avatarUrl, course e semester, e "to"
    opcional para o cartão inteiro virar link (nas configurações, /perfil).

  ProfileHeader.jsx
    Cabeçalho de perfil com capa, avatar, nome, username, bio, curso, data de
    entrada e contagem de seguindo/seguidores. Recebe titleId, user,
    followingCount, followerCount, onOpenRelation('following' | 'followers'),
    actions (botão no canto direito, como Seguir ou Editar perfil) e children
    (conteúdo extra abaixo das contagens, como mensagens de erro).

  ProfileSubjects.jsx
    Matérias do perfil em dois grupos: "Tenho dificuldade" (QUER_APRENDER) e
    "Posso ajudar" (DOMINA). Recebe subjects no formato de mockUserSubjects.
    Não renderiza nada quando a lista está vazia.

  ProfileActivityTabs.jsx
    Abas "Posts" e "Respostas" de um perfil. Recebe posts, comments,
    postCount e commentCount (opcionais; padrão é o tamanho das listas),
    currentUserId, reportReasons, onLikeChange, onReport, emptyPostsText e
    emptyCommentsText. Com likedPosts (e emptyLikedText), mostra também a aba
    "Curtidos"; só o perfil próprio passa essa lista.

  SubjectInterestPicker.jsx
    Seleção das disciplinas do perfil em dois grupos ("Tenho dificuldade" e
    "Posso ajudar"). Recebe subjects (catálogo), value (lista de
    { subject, interestType }), onChange e featuredIds. Mostra só as
    escolhidas e as sugeridas (featuredIds; no Editar perfil, as do semestre
    atual e do anterior; na Etapa 4 da criação de perfil, as do 1º). "Ver
    mais" abre a lista completa, agrupada por semestre, com busca por nome ou
    código. Uma disciplina fica em um só grupo, e cada grupo aceita até 5
    (contador "x/5"); ao tentar passar disso, mostra um toast de erro. As
    colunas dependem da largura do próprio componente: duas lado a lado em
    espaços largos (Editar perfil) e uma só em espaços estreitos (onboarding).

  Edição de perfil (src/pages/profile/EditProfilePage.jsx, rota
  /perfil/editar): usa FormField e SubjectInterestPicker. A foto já usa a
  API (updateAvatar/removeAvatar do useAuth, ao clicar em Salvar); o resto
  salva por src/services/accountService.js (mock, só em memória). O FeedLayout guarda
  currentUser e currentUserSubjects e fornece onProfileUpdate via Outlet
  context, atualizando também a autoria dos posts e respostas da conta.

  UsernameCard.jsx
    Bloco para trocar o username (em Configurações da conta). Recebe
    currentUser e onSaved(usuárioAtualizado). Converte para minúsculas e tira
    o "@" ao digitar, valida o formato e salva por
    accountService.updateUsername, que recusa username já em uso. Mostra um
    toast ao salvar. O username não é editado em Editar perfil.

  PasswordResetCard.jsx
    Bloco com o botão "Enviar link por e-mail" para alterar a senha com a
    conta logada. Recebe id, title (padrão "Senha") e label (padrão "Alterar
    senha"). Usa o hook src/hooks/usePasswordResetEmail.js, que chama
    accountService.sendPasswordResetEmail e mostra um toast com o resultado.
    Aparece em Configurações da conta e em Ajuda e suporte. A tela
    /recuperar-senha fica só para quem não está logado.

  Curtidas e salvos: o FeedLayout guarda likedByCurrentUser/likeCount e
  savedByCurrentUser no estado dos posts e fornece onLikeChange e
  onSaveChange via Outlet context. Toda página que mostra PostCard deve
  repassar os dois callbacks, para que curtir e salvar valham em todas as
  telas (a tela Salvos, /salvos, lista os posts com savedByCurrentUser).

  ProfileLink.jsx
    Link para o perfil de um usuário. Para a conta autenticada, leva a
    /perfil; para os demais, a /feed/users/:userId.

  Perfil próprio (src/pages/profile/MyProfilePage.jsx, rota /perfil) e perfil
  público (PublicProfilePage.jsx, rota /feed/users/:userId) usam os três
  componentes acima. O perfil próprio pode ser aberto pelo avatar do Header,
  pelo ProfileSummary da lateral (prop "to") e pelo cartão das configurações.

COMPONENTES DE POSTS — src/components/post/

  PostCard.jsx
    Apresenta uma publicação, incluindo autor, conteúdos relacionados, horário,
    quantidade de comentários, curtidas e ações.
    Recebe post com os dados da publicação e pode receber:
      detailsHref: destino para abrir o detalhe da dúvida; se omitido ou null,
        o conteúdo não navega.
      onLikeChange(postId, liked)
      onSaveChange(postId, saved)
      reportReasons: opções de denúncia disponíveis para essa tela.
      onReport(report): callback após confirmar denúncia.
    As ações de curtir e salvar possuem estado visual local. Quando a
    integração com a API for implementada, use os callbacks para comunicar a
    alteração ao componente pai/serviço. Aceita post.subjects como lista; também
    mantém compatibilidade com o formato singular post.subject. Ao denunciar,
    envia ao callback um objeto com reasonId, details, targetType e targetId.

  PostComposerModal.jsx
    Formulário modal para criar uma dúvida. Recebe subjects (disciplinas
    vindas da camada de dados/API), featuredSubjectIds (disciplinas exibidas
    primeiro; o FeedLayout passa as do perfil), onClose e onSubmit. Cada
    opção possui id (código, ex.: T390) e name; a seleção permite até 3
    disciplinas, com busca por nome ou código e "Ver mais" para a lista
    completa. O callback onSubmit recebe:
      { title, content, subjectIds }

  ReportPopup.jsx
    Modal reutilizável de denúncia. Recebe:
      reasons: lista da tabela auxiliar, com objetos { id, label }.
      targetLabel: nome do item denunciado, exibido no título do modal.
      onClose: callback para fechar.
      onSubmit: callback ao confirmar, recebe { reasonId, details }.
    O campo de detalhes é opcional. O componente não define a lista de motivos:
    cada tela fornece as opções por props, permitindo usar tabelas diferentes
    para posts, respostas, perfis ou outras entidades.

  PostReplyForm.jsx
    Formulário reutilizável de resposta à publicação principal. Recebe onSubmit
    com o texto da resposta. É usado somente no detalhe da dúvida; não deve ser
    renderizado dentro de PostReplyCard.

  PostReplyCard.jsx
    Apresenta uma resposta com a ação de denunciar. Respostas não recebem
    curtidas: no MVP, só os posts podem ser curtidos. Recebe:
      reply: dados da resposta, incluindo autor, content e createdAt.
      reportReasons: lista de motivos fornecida pela tela.
      onReport(report): callback após confirmar denúncia.
    Não oferece ação de resposta: respostas de outras pessoas não podem ser
    respondidas. Ao denunciar, usa ReportPopup e envia targetType "reply",
    targetId e postId no objeto do callback.

COMPONENTES DE AUTENTICAÇÃO — src/features/auth/components/

  AuthBrand.jsx, AuthCard.jsx, AuthField.jsx, AuthForm.jsx e AuthBackground.jsx
    Componentes da experiência de autenticação. Antes de criar outro campo,
    formulário ou cartão de autenticação, verifique se estes já atendem ao
    caso de uso. Os arquivos CSS da mesma pasta guardam estilos específicos
    desses componentes.


3. REGRA PRINCIPAL: SEPARAR COMPONENTE REUTILIZÁVEL DA PÁGINA/LAYOUT
-------------------------------------------------------------------

Se uma parte visual ou funcional de uma página puder ser usada em outras
telas, ela deve ser implementada como um componente separado em src/components/
(ou em src/features/ quando for específica de uma funcionalidade).

Não mantenha a implementação do componente reutilizável dentro do arquivo do
layout ou da página. A página/layout deve importá-lo e fornecer os dados por
props. Isso facilita a manutenção e permite que outras telas usem o mesmo
componente sem copiar código.

Exemplo de composição:

  // src/components/post/PostCard.jsx
  function PostCard({ post, children }) {
    return (
      <article>
        <h2>{post.title}</h2>
        <p>{post.content}</p>
        {children}
      </article>
    )
  }

  // Em uma página:
  <PostCard post={post}>
    <PostActions postId={post.id} />
  </PostCard>

Use props para dados e configurações. Use children quando o componente precisar
receber conteúdo interno variável, como ações, conteúdo complementar ou uma
área customizável. Não adicione children quando o componente não precisar dessa
flexibilidade.


4. RESPONSABILIDADE DE CADA CAMADA
----------------------------------

COMPONENTES (src/components/ e src/features/)
  Responsáveis por uma parte visual/funcional reutilizável. Devem receber os
  dados e callbacks necessários por props, em vez de depender dos dados de uma
  tela específica.

PÁGINAS (src/pages/)
  Responsáveis por montar o conteúdo de uma rota. A página escolhe quais
  componentes usar e fornece dados, estados e callbacks.
  Exemplo atual: src/pages/feed/FeedPage.jsx compõe PostCard com a lista de
  publicações e mostra uma mensagem quando a lista está vazia.
  src/pages/posts/PostDetailPage.jsx compõe a publicação, o formulário para
  responder à publicação principal e os PostReplyCard. Recebe pelo Outlet
  context a publicação, as respostas, os motivos de denúncia e callbacks.

LAYOUTS (src/layouts/)
  Responsáveis pela estrutura compartilhada entre várias páginas de uma área:
  fundo, cabeçalho, navegação, resumo do perfil e espaço da página filha.
  O layout deve compor componentes e informar suas props; não deve duplicar o
  código interno desses componentes.
  Exemplo atual: src/layouts/user/FeedLayout.jsx compõe Background, Header,
  MainNavigation e ProfileSummary e renderiza a página da rota com <Outlet />.
  src/layouts/user/PostDetailLayout.jsx organiza a navegação de retorno e
  fornece à tela os dados da dúvida e das respostas via Outlet context. O
  FeedLayout mantém os mocks e o estado local de posts, respostas e denúncias;
  os callbacks atualizam esse estado durante o desenvolvimento.

ROTAS (src/App.jsx)
  Associam caminhos a páginas e layouts. Uma página dentro de um layout deve
  ser configurada como rota filha para ser apresentada pelo <Outlet />.

DADOS (src/data/)
  Durante o desenvolvimento, mantenha dados de exemplo fora dos componentes
  visuais.
    mockPosts.js:
      mockPostsResponse: resposta simulada paginada de publicações.
      mockPostReportReasons: opções de denúncia para publicações e respostas.
    mockSubjects.js:
      mockSubjects: todas as disciplinas do curso, com id (código da
        disciplina, ex.: T390), name e semester (null = optativa). É a única
        fonte de disciplinas: posts, perfis, Explorar e formulários usam
        esses códigos. getSubjectById(código) devolve a disciplina.
    mockPostReplies.js:
      mockRepliesByPost: respostas agrupadas pelo id da publicação.
  Ao conectar o backend, substitua os mocks pela chamada apropriada em api/ ou
  services/, preservando os contratos de dados usados pelos componentes. A
  lista de motivos deve continuar sendo recebida por props e vir da tabela
  auxiliar apropriada para cada tipo de alvo.


5. PADRÃO DE CÓDIGO
-------------------

- Use React com arquivos .jsx para componentes e .js para módulos de dados ou
  utilitários sem JSX.
- Declare componentes como funções e exporte o componente principal como
  default, seguindo o padrão existente.
- Use nomes em PascalCase para componentes e nomes de arquivo, como PostCard.jsx.
- Use camelCase para props, funções, variáveis e propriedades dos dados.
- Use props para receber dados; evite embutir dados específicos de uma página
  dentro de um componente que pretende ser reutilizável.
- Use estado local (useState) para interações pertencentes ao próprio
  componente. Para estado compartilhado/persistido, use callbacks, contexts ou
  a camada de dados conforme a necessidade.
- Em componentes reutilizáveis de denúncia, receba a lista de opções por props;
  não fixe no popup categorias que possam variar de acordo com o tipo de alvo.
- Prefira classes utilitárias Tailwind, tokens de cor Companion e padrões de
  espaçamento já usados no projeto. Para estilos específicos maiores, mantenha
  CSS junto à funcionalidade correspondente, seguindo o padrão de features/auth.
- Inclua semântica e acessibilidade: elementos HTML adequados, labels, nomes
  acessíveis para botões apenas com ícone, estados como aria-pressed e
  aria-hidden em ícones decorativos.
- Use keys estáveis ao renderizar listas (por exemplo, o id do post).
- Não adicione dependências ou abstrações sem necessidade; reutilize os
  componentes já existentes antes de criar duplicatas.


6. COMO ADICIONAR UMA NOVA TELA
-------------------------------

1. Crie o arquivo da página dentro da pasta apropriada em src/pages/.
2. Identifique partes que possam ser compartilhadas com outras páginas. Crie
   cada uma em src/components/ ou src/features/, recebendo dados por props.
3. Se a nova página pertencer a uma área com estrutura compartilhada, use o
   layout existente em src/layouts/ ou crie/ajuste um layout que apenas componha
   componentes comuns e apresente o <Outlet />.
4. Registre a rota em src/App.jsx.
5. Mantenha dados de demonstração em src/data/ e chamadas reais à API em
   src/api/ ou src/services/.
6. Rode os comandos de verificação na pasta frontend:
     npm run lint
     npm run build

8. SESSÃO E AUTENTICAÇÃO
------------------------

ARQUIVOS
  src/api/api.js
    Instância do axios usada por todos os services. Adiciona o cabeçalho
    "Authorization: Bearer <token>" em cada requisição e, quando a API
    responde 401 fora do login/cadastro, avisa o AuthContext para encerrar a
    sessão. A URL da API vem de VITE_API_BASE_URL (arquivo frontend/.env).
  src/contexts/AuthContext.jsx
    Guarda a sessão (token + usuário) e expõe pelo hook useAuth():
      user, isAuthenticated, isRestoring, login, register, updateProfile,
      updateAvatar, removeAvatar, completeOnboarding e logout.
    updateProfile envia só os campos informados; os que ficam de fora não
    mudam no backend (cada etapa do onboarding salva só a sua parte).
  src/services/profileService.js
    Chamadas de /api/users/me. Também guarda as regras da foto de perfil,
    iguais às do backend: JPG, PNG ou WEBP com até 2 MB (getAvatarFileError).
    Arquivo inválido mostra um toast na hora da escolha; se a API ainda assim
    responder 413, a tela mostra o mesmo toast do limite de 2 MB.
  src/components/common/RequireAuth.jsx
    Protege as rotas internas em App.jsx: sem sessão, manda para /login; com
    perfil incompleto, manda para /onboarding/etapa-1; enquanto a sessão está
    sendo restaurada, mostra "Carregando sessão...".

COMO A SESSÃO SOBREVIVE AO F5 (SOLUÇÃO PROVISÓRIA)
  O backend devolve um JWT (access token) no login e no cadastro, válido por
  60 minutos. Para a apresentação do projeto, o token é salvo no localStorage
  do navegador, na chave "companion.accessToken":

    login/cadastro -> salva o token no localStorage
    F5             -> AuthContext lê o token salvo e chama GET /api/users/me
                      200: sessão restaurada com os dados atuais do usuário
                      401: token expirado, apaga o token e volta ao login
                      sem resposta: volta ao login (API fora do ar)
    sair da conta  -> logout() apaga o token da memória e do localStorage

  Para sair, sempre chame logout() do useAuth(); apenas navegar para /login
  deixa o token salvo e a pessoa continua logada.

  LIMITAÇÕES
  - Segurança: qualquer script que rode na página consegue ler o
    localStorage. Se o site tiver uma falha de XSS, o token pode ser roubado
    e usado até expirar. Por isso esta solução é apenas para demonstração.
    Nunca use dangerouslySetInnerHTML com conteúdo vindo de usuários.
  - Expiração: não há renovação automática. Depois de 60 minutos do login, a
    próxima chamada à API recebe 401 e a pessoa precisa entrar de novo.

SOLUÇÃO DEFINITIVA (PRODUÇÃO)
  Access token de vida curta (~15 min) somente em memória + refresh token de
  vida longa em cookie HttpOnly; Secure; SameSite=Strict, que o JavaScript não
  consegue ler. Exige mudanças no backend:
    - entidade RefreshToken salvando só o hash do token (mesmo padrão de
      PasswordResetToken), com validade e revogação;
    - login/cadastro enviando o cookie; novos POST /api/auth/refresh (gera um
      novo access token e troca o refresh token, invalidando o anterior) e
      POST /api/auth/logout (revoga o token e apaga o cookie);
    - revogar os refresh tokens ao excluir a conta ou redefinir a senha.
  No frontend: axios com withCredentials: true; ao abrir a página, chamar
  /auth/refresh no lugar de GET /users/me; no 401, renovar uma única vez e
  repetir a requisição. As alterações ficam concentradas em AuthContext.jsx
  e api.js, e o estado isRestoring e o logout() continuam valendo.
